Design Rationale

CI Challenges

Modern Continuous Integration (CI) keeps contributions flowing, but C++ projects face unique friction. The goal of this section is to restate the problem space—continuous integration requirements and the realities of testing C++ libraries—so that the design choices in the rest of the document remain grounded.

CI Basics

Continuous Integration automatically builds, tests, and integrates code multiple times a day so teams can detect defects early, keep the main branch deployable, and coordinate contributions across time zones.

graph TD A[Code Changes] -->|Commit| B[CI Server] B -->|Automated Build| C[Run Tests] C -->|Test Results| D[Deploy/Integrate] D -->|Deployment Status| E[Notify Team] E -->|Feedback| A
Figure 1. Continuous Integration Pipeline

Key takeaways for open source maintainers:

  • Shared velocity: automated checks keep the main branch releasable even with high contributor churn.

  • Fast review loops: maintainers receive immediate pass/fail feedback, reducing manual triage.

  • Trustworthy releases: consistently tested artifacts are more likely to ship without regressions.

C++ Pain Points

Testing C++ code spans multiple compilers, standard libraries, language versions, operating systems, and architectures. Long compile times and hardware-specific behavior increase the testing burden compared to higher-level languages such as JavaScript or Python, where narrower CI matrices often suffice with one Linux and one Windows job.

graph LR A[Matrix] -->|Windows| C1[Tests] A[Matrix] -->|Linux| C2[Tests] C1 --> D[Results] C2 --> D[Results] D --> F[Deploy/Integrate] D --> G[Notify Team]
Figure 2. A typical CI workflow for a JavaScript or Python project

For C++, the environment is guilty until proven innocent: a workflow that succeeds on one compiler version can break on the next minor release. Developers cannot practically reproduce every environment locally, so CI must stand in for platform coverage.

Key Factors

The C++ testing space is a factorial experiment across many dimensions:

Factor

Typical Values

Compiler

GCC, Clang, MSVC, MinGW, clang-cl, Apple Clang

Compiler Version

GCC 4–13, Clang 4–17, MSVC 2017–2022

Standard Library

libstdc++, libc++, MSVC STL

C++ Standard

C++11, C++14, C++17, C++20, C++23

Platform

Ubuntu, Windows, macOS, cross-compilation targets

Feature Flags

Sanitizers, coverage, time-trace, architecture toggles

These factors reveal why naive CI matrices explode combinatorially and why we must deliberately sample environments without losing coverage guarantees.

Combinatorial Risk

Not all factor combinations are valid or even meaningful:

  • A compiler factor only pairs with versions of the same compiler.

  • Most compilers—aside from Clang—should only be verified against their native standard library.

  • Each compiler targets a narrow set of supported operating systems and architectures.

  • Feature flags such as sanitizers or time-trace apply only when the underlying toolchain supports them.

Even after applying those filters, the illustrative matrix in the design above still demands 866,304 CI jobs. That volume is a classic combinatorial explosion—throwing more hardware, time, or budget at the problem is unsustainable. Pruning a few extra cases is equally insufficient; without a systematic design, important interactions remain untested. The solution must shrink the matrix so coverage grows roughly linearly with test count, redundancy drops, and critical combinations stay on the radar.

Ecosystem Impact

When C++ projects skip coverage for specific platforms or toolchains, downstream consumers shoulder the risk through broken integrations, delayed releases, or forced forks. Community ecosystems (package managers, conan/vcpkg registries, distro maintainers) require reproducible CI signals to trust updates, so gaps in testing ripple outward and slow the adoption of modern standards.

Workflow Reuse

Maintainers often inherit legacy scripts, copy complex workflows between repositories, and spend hours adapting them to new requirements. Without reusable building blocks, every project re-implements cache priming, dependency setup, and reporting logic, leading to fragmented practices and inconsistent diagnostics across the ecosystem.

Action Toolkit

The repository solves the coverage challenge by packaging reusable GitHub Actions that compose into a tailored CI pipeline. Instead of one monolithic action, the project offers specialized building blocks so teams can mix only what they need while inheriting best practices.

Matrix Flow

The C++ Matrix Action converts stated library requirements into an actionable matrix. It automates fractional factorial designs, ensuring representative coverage while keeping workflows tractable.

graph LR R[Requirements] -->|Contract| A[Matrix] A[Matrix] -->|Environment 1| B1[Install Dependencies] A[Matrix] -->|Environment 2| B2[Install Dependencies] A[Matrix] -->|...| B3[Install Dependencies] B1 --> C1[Tests] B2 --> C2[Tests] B3 --> C3[Tests] C1 --> D[Reports] C2 --> D[Reports] C3 --> D[Reports] D --> F[Deploy/Integrate] D --> G[Notify Team] style A fill:#cccccc,stroke:#000000,stroke-width:2px
Figure 3. A typical C++ Actions workflow

Highlights of the matrix action:

  • Contract-first: you declare supported compilers, standards, and platforms as the contract your library upholds.

  • Factor awareness: requirement factors drive fractional factorial sampling so every critical interaction is exercised.

  • Action-aware outputs: each matrix entry exposes flags like is-latest, is-main, and factor booleans that steer conditional steps.

  • Action suggestions: generated fields such as runs-on, container, cxxflags, and install provide opinionated defaults that teams can adopt or override.

Each generated matrix entry captures the compiler identity, version components, applicable C++ standards, and optional hints for sanitizer runs, coverage, or architecture-specific tweaks. Auxiliary flags expose factor membership, latest/earliest status, and positional hints, while supplemental fields surface recommended runners, containers, and toolchain flags. Users can copy the full YAML matrix for deeper customization when necessary.

Action Building Blocks

Independent actions implement the stages implied by the matrix:

graph TD subgraph For Each Entry B C D E end R[Requirements] --> A[Matrix] A[Matrix] --> B B[Setup C++] --> C C[Install Dependencies] --> D D[Workflows] --> E E[Reports] -->|success| F[Deploy/Integrate] E -->|failure| H[Notify Team] style A fill:#cccccc,stroke:#000000,stroke-width:2px
Figure 4. CI workflow using the C++ Actions

  • Compiler setup actions (setup-cpp and compiler-specific variants) locate or install the requested toolchain via native package managers before falling back to direct downloads, returning canonical compiler paths and versions.

  • Package setup actions (setup-apt, setup-vcpkg, Boost helpers, and generic installers) standardize dependency acquisition across environments with the same find-install-download sequence.

  • Workflow actions such as CMake Workflow and B2 Workflow encapsulate configure/build/test/install loops, adapt to declared cmake_minimum_required, and surface knobs for integration runs or Boost-specific flows.

  • Analysis actions capture metrics like compile time, coverage, or flamegraphs, typically toggled by matrix factors (e.g., enabling time-trace with extra compiler flags and the flamegraph step).

Origins

The project evolved from a GitHub Actions port of boost-ci. Growth milestones include:

  • Adding caching, parallelism, and cross-compilation features that are fragile in ad-hoc bash.

  • Surfacing frequently requested toggles (advanced CMake options, specialized Boost settings).

  • Promoting erstwhile bespoke scripts—coverage reporting, changelog generation—into maintained actions.

  • On-boarding new compilers and platforms early so the ecosystem can experiment safely.

This history explains why cmake-workflow stays general-purpose while b2-workflow remains tailored to Boost libraries.

Design Principles

The design rationale connects the challenges from the first section with the modular toolkit from the second. Independent actions remain the central promise: every setup, build, or report step ships as its own action so maintainers can compose only the stages they need, replace long bespoke scripts with a few YAML lines, or drop a single action into an existing workflow without dragging in the rest of the stack. Each action exposes inputs for every assumption—toolchain discovery, package ordering, workflow arguments, report toggles—so nothing is hard-coded and teams can override defaults on a per-job basis.

This independence carries through all categories introduced earlier. Compiler setup actions search the host, fall back to system package managers, and only then download binaries, ensuring matrix jobs mirror real user environments while still letting you pin a specific version and capture the resolved path as output. Package installers reuse the same discovery/install pattern across APT, vcpkg, Boost modules, or arbitrary archives, keeping dependency steps reusable yet customizable. Workflow actions such as CMake and B2 encapsulate configure-build-test-install loops, expose knobs to extract cmake_minimum_required, flip integration test gates, or provide Boost-specific tooling, and allow conditional execution per matrix entry. Analysis actions—coverage, flamegraphs, time-trace—stay optional, typically guarded by matrix factors so specialists can enable them without burdening every job.

mindmap root((cpp-actions)) Compose Actions combine independent steps align pipelines to contracts Reuse Templates start from shared blueprints adapt workflows together Scale Coverage curb matrix growth focus on critical factors Share Practices encode best defaults onboard new toolchains
Figure 5. Composable Architecture

Core principles:

  • Compose independent actions so maintainers assemble only the steps their contracts require, turning long bash workflows into modular YAML while keeping every assumption overrideable.

  • Reuse curated templates by cloning common action stacks, keeping workflows consistent yet easy to tailor across compilers, packages, build systems, and reporting steps.

  • Scale coverage deliberately with matrix guidance that reins in the 866,304-case explosion while still exercising the combinations that matter.

  • Share proven practices through inputs, hints, and the “find → package manager → download” install flow so CI mirrors real user environments without imposing a single configuration.
