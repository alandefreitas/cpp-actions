= Contributor Guide

If there's a platform where one of the actions does not work, feel free to submit a PR with adaptations and tests.

== Quick Contribution Path

* **Ground yourself in the design rationale:** Remember that every action stays independent and overrideable—nothing is hard-coded for a single project, and contributors are expected to compose the pieces that fit their workflows rather than baking in assumptions.
* **Review the action metadata:** Read `<action-name>/action.yml` before changing behavior so your updates match the documented inputs and outputs.
* **Understand the layout:** Each GitHub Action lives in its own top-level directory (for example `setup-cmake/`, `cmake-workflow/`, or `cpp-matrix/`). Make your edits inside the action you are targeting so changes stay scoped.
* **Edit source files:** Update code under the `<action-name>` directory and leave generated assets alone until you rebuild with the provided scripts (see below).
* **Run focused checks:** Execute `npm run all --prefix <action-name>` to reinstall dependencies, rebuild the bundle, and run Jest for that action.
* **Validate the full suite:** Finish by running `./build.sh` at the repository root to regenerate every action bundle and rerun all tests.
* **Commit regenerated artifacts:** Include the refreshed `<action-name>/dist` output in the same commit as your source changes so the published action matches the repository.

== Maintain Documentation

* **Edit narrative pages directly:** Update prose in `docs/modules/ROOT/pages/*.adoc` when you need long-form guidance like this contributor guide.
* **Treat `action.yml` as the source of truth:** Each action's metadata feeds the autogenerated reference pages, so document new inputs, outputs, and examples there first.

== Understand the Build Workflow

Contributing to the repository is relatively easy.
All actions are vanilla JavaScript.
The only caveat — especially for C++ programmers unfamiliar with the JavaScript ecosystem — is that the JavaScript code needs to be compiled, and the compiled output must be committed to the repository.
This is a requirement of how GitHub Actions work.
A `build.sh` script in the root directory iterates all actions, builds them, and runs the tests.

So far, we’ve accepted nearly all contributions — except those that break composability or introduce hard-coded values tied to a specific library.

== Verify in CI

The ultimate test is whether it works in CI.
The ci.yml workflow exercises all actions with all supported features, using a toy project that's quick and inexpensive to compile.
So, we spend little time testing the actions here instead of finding bugs while trying to use the actions for other real libraries that are much more expensive to test.

Each action also has an `index.test.js` where we can test the internal logic of more complex functions.
It's impossible to replicate the environment perfectly in these tests, so the ultimate test is always CI.

As a result, it's common to test the entire repository by pushing changes to a branch and observing the results in CI.
If needed, we iterate via force-pushes until the branch is ready for a PR.
In theory, we could use https://github.com/nektos/act[nektos/act] for that, but, at best, it won't cover all environments.
