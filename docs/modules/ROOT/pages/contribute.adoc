= Contributor Guide

If there's a platform where one of the actions does not work, feel free to submit a PR with adaptations and tests.

== Developer Workflow

[source,bash]
----
git clone https://github.com/alandefreitas/cpp-actions.git
cd cpp-actions
npm install
npm test
npm run lint
----

== Quick Contribution Path

* **Ground yourself in the design rationale:** Remember that every action stays independent and overrideable—nothing is hard-coded for a single project, and contributors are expected to compose the pieces that fit their workflows rather than baking in assumptions.
* **Review the action metadata:** Read `<action-name>/action.yml` before changing behavior so your updates match the documented inputs and outputs.
* **Understand the project layout:** Each GitHub Action lives in its own top-level directory (for example `setup-cmake/`, `cmake-workflow/`, or `cpp-matrix/`). Make your edits inside the action you are targeting so changes stay scoped.
* **Edit source files:** Update TypeScript code under `<action-name>/src/` and leave generated assets alone until you rebuild with the provided scripts (see below).
* **Run focused checks:** Execute `npm run build -w <action-name>` to rebuild the bundle, then `npx jest --selectProjects <action-name>` to run tests for that action.
* **Validate the full suite:** Finish by running `npm run build` at the repository root to recompile all workspaces, then `npm test` and `npm run lint` to verify.
* **Commit regenerated artifacts:** Include the refreshed `<action-name>/dist` output in the same commit as your source changes so the published action matches the repository.

== Maintain Documentation

* **Edit narrative pages directly:** Update prose in `docs/modules/ROOT/pages/*.adoc` when you need long-form guidance like this contributor guide.
* **Treat `action.yml` as the source of truth:** Each action's metadata feeds the autogenerated reference pages, so document new inputs, outputs, and examples there first.

== Understand the Build Workflow

Contributing to the repository is relatively easy.
All actions are written in TypeScript, which compiles to JavaScript and is then bundled into a single file using https://esbuild.github.io/[esbuild].
The only caveat — especially for C++ programmers unfamiliar with the JavaScript ecosystem — is that the compiled output must be committed to the repository.
This is a requirement of how GitHub Actions work.

The repository uses https://docs.npmjs.com/cli/v10/using-npm/workspaces[npm workspaces] to manage dependencies across all packages.
A single `npm install` at the root installs dependencies and compiles all actions (via the `prepare` lifecycle hook).
Use `npm run build` to recompile, `npm test` to run tests, and `npm run lint` to lint documentation.

So far, we've accepted nearly all contributions — except those that break composability or introduce hard-coded values tied to a specific library.

== Verify in CI

The ultimate test is whether it works in CI.
The ci.yml workflow exercises all actions with all supported features, using a toy project that's quick and inexpensive to compile.
So, we spend little time testing the actions here instead of finding bugs while trying to use the actions for other real libraries that are much more expensive to test.

Each action also has an `index.test.ts` where we can test the internal logic of more complex functions.
It's impossible to replicate the environment perfectly in these tests, so the ultimate test is always CI.

As a result, it's common to test the entire repository by pushing changes to a branch and observing the results in CI.
If needed, we iterate via force-pushes until the branch is ready for a PR.
In theory, we could use https://github.com/nektos/act[nektos/act] for that, but, at best, it won't cover all environments.

== npm Scripts Reference

The root `package.json` provides the following scripts for development and maintenance.

NOTE: The naming follows npm conventions where `prepare` is a lifecycle hook that runs automatically after `npm install`.
In this repo, `prepare` compiles and bundles all workspaces. `build` is an alias for `prepare` for manual use.
Each script does one thing — use `npm run validate` for the full check.

=== Build and Test

[cols="1,2,2"]
|===
|Script |Description |Usage

|`prepare`
|Compiles TypeScript and bundles with esbuild across all workspaces. Runs automatically after `npm install`.
|`npm run prepare`

|`build`
|Recompiles everything (alias for `prepare`, for manual use). Also available per-workspace.
|`npm run build` +
`npm run build -w <workspace>`

|`test`
|Runs Jest tests across all workspaces.
|`npm test` +
`npx jest --selectProjects <name>`

|`test:coverage`
|Runs tests with coverage reporting.
|`npm run test:coverage`

|`lint`
|Lints JSDoc comments across all workspaces.
|`npm run lint`

|`docs`
|Generates documentation (Python deps + parse_actions.py + Antora).
|`npm run docs`

|`update-data`
|Fetches compiler tags, ubuntu versions, and boost dependency data.
|`npm run update-data`

|`validate`
|Runs the full validation suite: update-data + build + test + lint.
|`npm run validate`
|===

=== Dependency Management

[cols="1,2,2"]
|===
|Script |Description |Usage

|`depcheck`
|Checks for unused or missing dependencies in all workspaces.
|`npm run depcheck`

|`update-deps`
|Updates all dependencies to their latest versions using npm-check-updates.
|`npm run update-deps`
|===

=== Version and Release

[cols="1,2,2"]
|===
|Script |Description |Usage

|`version:set`
|Sets the version across the root package and all workspaces.
|`npm run version:set -- <version>` +
Example: `npm run version:set -- 1.9.0`

|`release`
|Interactive release workflow. Prompts for version (patch/minor/custom based on commits since last tag), updates versions, rebuilds, runs checks, then pushes to master and creates a git tag.
|`npm run release` +
`npm run release -- --dry-run` +
`npm run release -- --version <ver>`
|===
